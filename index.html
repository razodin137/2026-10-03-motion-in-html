Twenty CRM — what a BaaS never ships

A database is not an application.

Supabase, Baserow, NocoDB, plain Postgres — all of it is passive infrastructure: a store, some auth, an API, waiting for a frontend you have not written yet. A real CRM is the active half: workers that poll, parse, resolve and link, with a purpose-built front end over the same rows.

Polling is the tip of the iceberg

THE "I COULD BUILD THIS IN A WEEKEND" TRAP

01 · PROTOCOLS

IMAP was not designed for your schema

Raw MIME strings, base64 attachments, chaotic HTML signatures, infinitely nested threads — plus provider rate limits and connections that drop mid-fetch.

parse(MIME) → text · parts · thread
02 · CALENDARS

Recurrence is a state machine

“Every Tuesday, except next Tuesday, which moved to Wednesday.” RRULE parsing, timezone offsets, DST shifts and attendee RSVP states, forever.

RRULE · TZID · DST · PARTSTAT
03 · RESOLUTION

Who is john.doe@…?

Known contact? Known company domain? Auto-create or not? Ignore noreply@, split multi-recipient threads, merge the dupe when he writes from his personal address.

match → create → merge → suppress
04 · THE VIEW

A SQL view is not a timeline

One company record has to interleave emails, meetings, notes and stage changes, chronologically. That needs join logic and a UI layer built for the shape.

JOIN ≠ TIMELINE
BUILD IT IFyou want a static, read-only rolodex USE THE CRM IFyou need to act on the data
